# Java / Spring 학습

문법을 하나씩 외우지 않고, **실제 프로젝트의 기능 흐름을 따라가며** 필요한 Java/Spring 개념을 익힌다.
목표는 "코드를 읽었다"가 아니라 **"코드 없이 흐름을 내 말로 설명할 수 있다"**이다.

---

## 프로젝트 목록

| 프로젝트 | 내용 | 학습 문서(`docs/`) | 상태 |
|---|---|---|---|
| `tut-rest` | Spring 공식 가이드 "Building REST services with Spring". `nonrest` → `rest` → `evolution` → `links` 4단계 모듈 | ✅ 생성됨 | 진행 중 (`evolution`) |
| `spring-boot-jpa-postgresql` | Spring Boot + JPA + PostgreSQL | ⬜ 아직 없음 | 미시작 |
| `spring-boot-rest-api-postgresql` | Spring Boot REST API + PostgreSQL (Docker) | ⬜ 아직 없음 | 미시작 |

> 정확한 진도는 각 프로젝트의 `docs/HANDOFF.md`와 `docs/FEATURE_CHECKLIST.md` 체크 상태를 본다.

## 전체 학습 절차

```
① 체크리스트 생성  →  ② 튜터 수업 (반복)  →  ③ 세션 종료 시 HANDOFF + 오답노트 저장  →  ④ 다음 세션에서 오답 복습 후 이어서
```

### ① 새 프로젝트를 시작할 때: 체크리스트 생성

1. 프로젝트 폴더에서 Claude Code를 연다.
2. 이 문서 맨 아래의 **"각 프로젝트 학습 체크리스트생성 프롬프트"**를 그대로 붙여 넣는다.
3. 결과로 `docs/`에 두 문서가 생긴다.

| 문서 | 기준 | 용도 |
|---|---|---|
| `FEATURE_CHECKLIST.md` | **기능 흐름** (요청 → 코드 → DB → 응답) | **공부할 때 보는 메인 교재** |
| `CODE_COVERAGE.md` | **클래스 / 메서드** | 모듈(단계) 하나를 끝낼 때마다 **빠진 게 없는지 점검** |

> 처음부터 `CODE_COVERAGE.md`로 공부하면 클래스를 외우는 방식이 되기 쉽다. 흐름은 `FEATURE_CHECKLIST.md`로 공부한다.

### ② 수업 진행

Claude에게 "공부 시작하자" 또는 "공부 이어서 하자"라고 말하면 아래 **수업 방식**대로 진행된다.

### ③ 그날 공부를 끝낼 때

**"오늘은 여기까지"**라고 말하면 Claude가 아래 두 문서를 함께 정리한다.

| 문서 | 저장되는 내용 |
|---|---|
| `docs/HANDOFF.md` | 진행 상황, 멈춘 곳(답하지 못한 질문), 다음 순서 |
| `docs/WRONG_ANSWERS.md` (오답노트) | 그날 틀렸거나 헷갈린 내용, 약점 패턴 표 갱신, 다시 맞힌 항목 `재확인` 체크 |

오답노트에 기록하는 기준:
- 틀린 답 (예: 어노테이션을 메서드라고 답함)
- 결과는 맞췄지만 **이유**가 틀린 답 (예: DELETE가 200인 이유)
- "이해가 안 간다"고 말한 개념 (다시 설명해서 이해했더라도 기록)
- 질문과 다른 것에 답하거나 값을 빠뜨리는 **답변 습관**
- 실험 절차 실수 (예: 코드를 고치고 재시작하지 않음)

각 오답은 **내가 적은 답 / 정답 / 왜 헷갈렸나 / 구분법 / 재확인** 형식으로 남긴다. 맨 위의 **"약점 패턴"** 표를 보면 내가 어떤 종류의 실수를 반복하는지 한눈에 알 수 있다.

### ④ 다음 세션

"공부 이어서 하자"라고 말한다. Claude는 이렇게 진행한다.
1. `docs/HANDOFF.md`와 `docs/WRONG_ANSWERS.md`를 읽는다.
2. 오답노트에서 **아직 `재확인`이 안 된 항목 1~2개**를 복습 질문으로 먼저 낸다. 맞히면 `[x]`로 체크한다.
3. HANDOFF의 멈춘 곳부터 수업을 이어서 진행한다.

## 수업 방식

### 기본 사이클: 한 번에 한 주제

| 단계 | 누가 | 내용 |
|---|---|---|
| 1. 보여주기 | Claude | 관련 코드 몇 줄 + 짧은 설명 (코드 주석에 ①②③ 번호) |
| 2. 직접 해보기 | 나 | 서버를 켜고 브라우저나 PowerShell로 요청 보내기, 코드 한 줄 바꿔 보기 → 재시작 → 결과 확인 |
| 3. 질문에 답하기 | 나 | 빈칸 양식에 짧게 답한다. 모르면 `?` 또는 "모르겠어" |
| 4. 피드백 | Claude | 맞은 점을 먼저 말하고, 틀린 부분은 **적은 답 / 정답 / 이유**로 고친다 |
| 5. 진도 기록 | Claude | 설명할 수 있게 된 항목을 `FEATURE_CHECKLIST.md`에 `[x]`로 체크. 틀린 내용은 세션 종료 때 오답노트에 기록 |

### 답변 양식

Claude가 질문을 빈칸 형태로 주면, 빈칸만 채워서 보낸다. 완벽한 문장이 아니어도 된다.

```
1. 요청이 처음 도착하는 메서드:
2. 그 메서드가 DB에서 찾으려고 호출하는 것:
3. ...:
```

### 수업 원칙

- **한 번에 하나씩.** 질문은 1~3개만 낸다. 여러 개를 한꺼번에 주면 오히려 감이 안 온다.
- **요청에서 출발한다.** "앱이 어떻게 켜지나"보다 "내가 보낸 요청이 어디로 가나"부터 본다. 그래야 쉽다.
- **Java인지 Spring인지 구분한다.** 이 개념이 Java 문법인지(람다, 제네릭, `Long`), Spring이 대신 해 주는 기능인지(`@GetMapping`, 의존성 주입, Repository 구현) 매번 구분해서 설명한다.
- **추측보다 실행.** 예상을 먼저 말해 보고, 실제로 돌려서 확인한다. 문서 내용도 실행 결과와 다르면 문서를 고친다.
- **깨뜨려 보기.** 어노테이션 한 줄을 주석 처리해 보고 무엇이 망가지는지 본다. 예: `@RestControllerAdvice`를 빼면 404가 500이 된다. 실험이 끝나면 반드시 원래대로 되돌린다.
- **단계형 프로젝트는 차이만 본다.** 다음 단계로 넘어가면 처음부터 다시 읽지 않고 **"뭐가 바뀌었지?"**만 본다.
- **비유를 쓴다.** 어노테이션은 표지판, `Optional`은 상자, Stream은 컨베이어 벨트, `EntityModel`/`CollectionModel`은 작은 상자/큰 상자.
- **코드 수정은 내가 한다.** Claude는 문서(`docs/`)만 수정하고, 소스 코드는 내가 요청할 때만 바꾼다.

### 자주 쓰는 명령 (Windows PowerShell)

```powershell
# 서버 실행 (tut-rest 예시, 모듈명만 바꿔서 사용)
.\mvnw.cmd -pl nonrest spring-boot:run

# GET: 브라우저에서 http://localhost:8080/employees

# POST / PUT
Invoke-RestMethod -Method Post -Uri http://localhost:8080/employees -ContentType 'application/json' -Body '{"name":"Samwise Gamgee","role":"gardener"}'

# 상태코드 확인 (DELETE 등)
(Invoke-WebRequest -Method Delete -Uri http://localhost:8080/employees/4 -UseBasicParsing).StatusCode
```

- 코드를 고치면 **서버를 재시작**해야 반영된다 (`Ctrl + C` → 다시 실행).
- 같은 포트(8080)를 쓰는 서버는 동시에 하나만 켤 수 있다.

## 프로젝트별 `docs/` 구성

```
<프로젝트>/docs/
├── FEATURE_CHECKLIST.md   # 기능 흐름 체크리스트 (메인 교재, 진도 체크)
├── CODE_COVERAGE.md       # 클래스/메서드 커버리지 (단계별 점검)
├── HANDOFF.md             # 세션 인수인계 (역할, 진행 상황, 멈춘 곳, 다음 순서)
└── WRONG_ANSWERS.md       # 오답노트 (틀린 답, 헷갈린 개념, 약점 패턴, 재확인 체크)
```

- `FEATURE_CHECKLIST.md`, `CODE_COVERAGE.md`: 맨 아래 프롬프트로 생성한다.
- `HANDOFF.md`, `WRONG_ANSWERS.md`: 첫 수업 세션이 끝날 때 Claude가 만든다.

# 각 프로젝트 학습 체크리스트생성 프롬프트


현재 이 프로젝트를 Java/Spring 학습용으로 분석하려고 한다.

내 학습 방식은 문법을 하나씩 외우는 방식이 아니라, 프로젝트 전체의 기능 흐름과 코드 로직을 따라가면서 필요한 Java/Spring 개념을 이해하는 방식이다.

이 프로젝트의 전체 코드를 분석해서 `docs` 디렉터리에 아래 2개의 문서를 만들어줘.

## 1. `FEATURE_CHECKLIST.md`

프로젝트의 기능과 실행 흐름을 기준으로 학습 체크리스트를 작성한다.

단순히 파일이나 메서드를 나열하지 말고, 사용자의 요청이나 애플리케이션 동작이 실제로 어떤 코드 흐름을 거치는지 기준으로 기능을 나눠라.

예:

- 전체 데이터 조회
- 단일 데이터 조회
- 데이터 생성
- 데이터 수정
- 데이터 삭제
- 예외 처리
- Validation
- 초기 데이터 로딩
- 인증/인가
- DB 저장 및 조회 흐름

단, 위 항목을 기계적으로 넣지 말고 실제 프로젝트에 존재하는 기능만 분석해서 작성한다.

각 기능은 다음 형식으로 작성한다.

```md
## 기능명

- [ ] 이 기능의 목적을 설명할 수 있다.
- [ ] 요청이 처음 들어오는 지점을 찾을 수 있다.
- [ ] Controller → Service → Repository → DB 등의 실제 호출 흐름을 설명할 수 있다.
- [ ] 이 과정에서 사용되는 주요 Java/Spring 문법과 개념을 설명할 수 있다.
- [ ] 데이터가 어떤 객체로 전달되고 변환되는지 설명할 수 있다.
- [ ] 최종 응답이 어떻게 만들어지는지 설명할 수 있다.
- [ ] 코드를 보지 않고 전체 흐름을 내 말로 설명할 수 있다.
```

프로젝트 구조에 Service 계층이 없는 등 실제 구조가 다르면 실제 코드 구조에 맞게 작성한다.

각 기능 아래에는 반드시 실제 관련 클래스와 주요 메서드를 적어라.

예:

```md
### 관련 코드
- `EmployeeController#all()`
- `EmployeeRepository#findAll()`
- `Employee`
```

기능은 너무 작은 메서드 단위로 쪼개지 말고, 하나의 의미 있는 동작 흐름을 기준으로 묶어라.

## 2. `CODE_COVERAGE.md`

프로젝트 전체 코드에서 내가 아직 이해하지 못한 부분이 남지 않도록 코드 학습 커버리지를 관리하는 문서를 작성한다.

프로젝트의 학습 가치가 있는 Java 코드 전체를 분석해서 다음 계층으로 정리한다.

```md
## 파일명 또는 클래스명

### 역할
이 코드가 프로젝트에서 담당하는 역할을 1~3줄로 설명

### 체크리스트
- [ ] 이 클래스가 왜 필요한지 설명할 수 있다.
- [ ] 주요 필드의 역할을 설명할 수 있다.
- [ ] 생성자가 있다면 왜 필요한지 설명할 수 있다.
- [ ] 주요 메서드의 역할을 설명할 수 있다.
- [ ] 다른 클래스와 어떤 관계인지 설명할 수 있다.
- [ ] 이 코드에서 사용된 주요 Java/Spring 개념을 설명할 수 있다.
```

그리고 주요 메서드는 별도로 나열한다.

```md
### 주요 메서드

- [ ] `all()`
  - 역할:
  - 호출되는 곳:
  - 호출하는 코드:
  - 사용 개념:

- [ ] `one(Long id)`
  - 역할:
  - 호출되는 곳:
  - 호출하는 코드:
  - 사용 개념:
```

단순 getter/setter, 자동 생성 코드, 의미 없는 boilerplate까지 모두 체크리스트로 만들지는 마라.

대신 프로젝트 흐름을 이해하는 데 필요한 클래스, 인터페이스, 설정, 주요 메서드는 빠짐없이 포함한다.

특히 다음 항목을 놓치지 마라.

- Entry Point
- Entity / DTO / Model
- Controller
- Service가 있다면 Service
- Repository
- Exception 및 Exception Handler
- Configuration
- 초기화 코드
- 주요 Interface
- 주요 Annotation이 붙은 클래스
- DB 및 외부 시스템과 연결되는 코드

## 문서 작성 원칙

이 문서의 목적은 "코드를 읽었다"를 기록하는 것이 아니라 "코드를 이해하고 설명할 수 있다"를 확인하는 것이다.

따라서 체크 항목은 가능하면 다음 기준을 따른다.

- 역할을 설명할 수 있는가?
- 왜 필요한지 설명할 수 있는가?
- 어디서 호출되는가?
- 무엇을 호출하는가?
- 데이터가 어디서 와서 어디로 가는가?
- 어떤 Java/Spring 개념이 사용되는가?
- 코드 없이 흐름을 설명할 수 있는가?

프로젝트 전체를 먼저 분석한 후 문서를 작성해라.

코드는 수정하지 말고 `docs/FEATURE_CHECKLIST.md`, `docs/CODE_COVERAGE.md` 두 파일만 생성해라.

마지막으로 두 문서가 프로젝트 전체의 주요 로직을 충분히 커버하는지 스스로 한번 검토하고, 빠진 주요 흐름이나 주요 클래스가 있다면 추가해라.
