## A. 이름 구분 (어노테이션 / 메서드 / URL / 링크)

### A-1. 어노테이션을 메서드라고 답함 ⚠️ 2회
- 날짜 / 모듈 / 주제: 2026-09-28 / nonrest / 단일 조회, 예외 처리
- 내가 적은 답: 요청이 도착하는 메서드 = `@GetMapping("/employees/{id}")`, 예외 처리 메서드 = `ExceptionHandler`
- 정답: `one()`, `employeeNotFoundHandler()`
- 왜 헷갈렸나: 어노테이션이 메서드 바로 위에 붙어 있어서 한 덩어리로 보였음
- 구분법: **`@`로 시작하면 표지판(어노테이션)**, **`이름(...) { }`이면 메서드**. 표지판은 Spring에게 주는 설명이고, 실제로 실행되는 건 그 아래의 메서드다.
  ```java
  @GetMapping("/employees/{id}")        // ← 표지판
  Employee one(@PathVariable Long id) {  // ← 메서드 (이게 실행됨)
  ```
- [ ] 재확인

### A-2. URL을 코드 호출이라고 답함
- 날짜 / 모듈 / 주제: 2026-09-28 / nonrest / 예외 처리 흐름
- 내가 적은 답: DB에서 찾으려고 호출하는 것 = `/employees/99`
- 정답: `repository.findById(99)`
- 구분법: **URL은 브라우저가 보내는 주소**, **코드 호출은 Java 코드 안의 `객체.메서드()`**. URL이 컨트롤러 메서드에 도착한 뒤, 그 메서드 안에서 `findById()`를 호출한다.
- [ ] 재확인

### A-3. `@GetMapping`과 `@PostMapping` 혼동
- 날짜 / 모듈 / 주제: 2026-09-28 / rest / 링크 주소 생성
- 내가 적은 답: self 링크 주소는 `@PostMapping("/employees/{id}")`를 보고 만들어진다
- 정답: `@GetMapping("/employees/{id}")`. `methodOn(...).one(id)`가 가리키는 `one()` 위에 붙은 어노테이션이다.
- 구분법: 링크 주소는 **`methodOn(...)` 뒤에 적힌 메서드 → 그 메서드 위의 어노테이션**을 보고 만들어진다. `@PostMapping`은 `newEmployee()` 위에 있고 주소에 `{id}`가 없다.
- [ ] 재확인

### A-4. `href`를 링크 이름이라고 답함
- 날짜 / 모듈 / 주제: 2026-09-28 / rest / HAL 구조
- 내가 적은 답: 2개 링크(self, href)
- 정답: 2개 링크(**self, employees**). `href`는 모든 링크 안에 있는 **주소 칸**이다.
- 구분법: `"self": { "href": "..." }` → 바깥이 **이름**, 안의 `href`가 **주소**
- [ ] 재확인

### A-5. 파라미터 타입을 `int`라고 말함
- 날짜 / 모듈 / 주제: 2026-09-28 / nonrest / 삭제
- 내가 적은 답: id가 int일 경우 지운다
- 정답: `@PathVariable Long id`이므로 **`Long`으로 바뀔 수 있는 값**일 경우
- 기억할 것: 타입은 코드에 적힌 그대로 말하기 (`Long` ≠ `int`)
- [ ] 재확인

## B. 방향과 순서 (요청↔응답, set↔get, 먼저↔나중)

### B-1. 예외 처리 순서를 반대로 말함
- 날짜 / 모듈 / 주제: 2026-09-28 / nonrest / 삭제 후 조회
- 내가 적은 답: Advice가 먼저 404로 처리하고, 그다음 Exception이 메시지를 생성한다
- 정답: **Exception이 먼저 메시지를 만들고 던져지고 → Advice는 마지막에 받는다**
  ```
  one(4) → findById(4) 없음 → new EmployeeNotFoundException(4) (메시지 생성) → throw → Advice가 받음 → 404
  ```
- 구분법: **던지는 쪽이 먼저, 받는 쪽이 나중.** 받을 게 없으면 받을 수도 없다.
- [ ] 재확인

### B-2. setName과 getName의 방향 혼동
- 날짜 / 모듈 / 주제: 2026-09-28 / evolution / name 하위 호환
- 내가 적은 답: `getName()`이 이름을 firstName/lastName으로 나눈다. `"Gandalf"`는 `getName`에서 에러가 난다.
- 정답: 나누는 건 **`setName()`**(요청이 들어올 때), 합치는 건 **`getName()`**(응답이 나갈 때)
- 구분법: **set = 넣는다 = 들어옴(요청)**, **get = 꺼낸다 = 나감(응답)**
- [x] 재확인 (확인 질문에서 순서를 맞게 답함, 2026-09-28)

### B-3. 요청과 응답 용어 혼동
- 날짜 / 모듈 / 주제: 2026-09-28 / nonrest / 예외 처리 흐름 요약
- 내가 적은 답: `/employees/99` (응답보냄)
- 정답: **요청**
- 구분법: **브라우저 → 서버 = 요청**, **서버 → 브라우저 = 응답**
- [ ] 재확인

### B-4. `run()`이 두 개라는 걸 구분하지 못함
- 날짜 / 모듈 / 주제: 2026-09-28 / nonrest / LoadDatabase
- 내가 적은 답: 람다 코드는 `run()`에서 실행된다
- 정답: `run()`이 두 개 있다.
  - `SpringApplication.run()`: `main()`에서 **앱 전체를 켠다**
  - `CommandLineRunner`의 `run()`: 앱이 다 켜진 뒤 **Spring Boot가 호출해서 람다를 실행한다**
- 기억할 것: `initDatabase()`는 Bean을 만들 때 **람다를 반환만** 한다. 실행은 나중이다. (실행 시점이 두 번)
- [ ] 재확인

### B-5. `parts` 배열을 "저장할 곳"으로 이해함
- 날짜 / 모듈 / 주제: 2026-09-28 / evolution / setName 한계
- 내가 적은 답: `parts[0]`에 Gandalf가 저장되고, `parts[1]`에 저장될 이름이 없다
- 정답: `parts`는 `split()`으로 **나눈 결과**이고, 거기서 **꺼내서** `firstName`/`lastName`에 저장한다. `parts[1]`은 꺼낼 게 없어서 예외가 난다.
- 구분법: `this.lastName = parts[1];` → **오른쪽에서 꺼내서 왼쪽에 넣는다**

## C. 상태코드의 원인

### C-1. DELETE가 200인 이유
- 날짜 / 모듈 / 주제: 2026-09-28 / nonrest / 삭제
- 내가 적은 답: id 4가 존재하기 때문에 200
- 정답: 메서드가 **`void`이고 예외 없이 끝났기 때문**. 없는 999를 지워도 200이다.
- 기억할 것: 결과가 같을 때 **다른 입력으로도 같은지** 비교해 보면 진짜 원인을 알 수 있다.
- [ ] 재확인

### C-2. 400을 "서버 에러"라고 부름
- 날짜 / 모듈 / 주제: 2026-09-28 / evolution / `"Gandalf"` POST
- 내가 적은 답: 400으로 서버에러가 뜬다
- 정답: **400 = 요청이 잘못됨 (클라이언트 탓)**, **500 = 서버 내부 오류**
- 기억할 것: 예외가 **요청을 읽는 단계**(`@PathVariable` 변환, `@RequestBody` JSON 변환)에서 나면 400이고, **메서드 안**에서 처리되지 않은 예외가 나면 500이다.

  | 요청 | 실패한 단계 | 결과 |
  |---|---|---|
  | `/employees/qwer` | `@PathVariable` 변환 | 400 |
  | `{"name":"Gandalf"}` | `@RequestBody` 변환 (`setName`) | 400 |
  | `/employees/99` | 메서드 안 → Advice | 404 |
  | Advice 없이 `/employees/99` | 메서드 안 → 처리 없음 | 500 |
- [ ] 재확인

### C-3. Advice를 빼면 "404만 뜬다"고 예상함
- 날짜 / 모듈 / 주제: 2026-09-28 / nonrest / Advice 제거 실험
- 내가 적은 답: 404만 뜰 것이다
- 정답: **500 + Whitelabel Error Page, 메시지 없음**
- 기억할 것: Spring은 `EmployeeNotFoundException`이 "없다"는 뜻이라는 걸 모른다. **처리되지 않은 예외는 무조건 500**이다. 404로 바꿔 주는 게 Advice의 역할이다.
- [x] 재확인 (실험으로 직접 확인함)

### C-4. `@RestController`를 빼면 "아무것도 안 뜬다"고 예상함
- 날짜 / 모듈 / 주제: 2026-09-28 / nonrest / 앱 시작
- 내가 적은 답: POST 자체가 작동하지 않고, 8080에 들어가도 아무것도 뜨지 않는다
- 정답: **GET/POST/PUT/DELETE 모두** 안 되고, 서버는 정상으로 켜져 있어서 **404 에러 페이지**가 뜬다.
- 기억할 것: 표지판이 없으면 Spring이 그 클래스를 Bean으로 만들지 않는다 → 매핑이 전부 사라진다 → "그런 주소 없음"(404)
- [ ] 재확인 (실험은 아직 안 함)

## D. Spring 내부 동작 (코드에 안 보이는 부분)

### D-1. 인터페이스가 어떻게 객체가 되는지 이해가 안 감
- 날짜 / 모듈 / 주제: 2026-09-28 / nonrest / Repository
- 내가 적은 답: "Spring Data가 구현 객체를 만들어 준다"는 게 무슨 말인지 모르겠다
- 정답: 인터페이스는 몸통이 없어서 `new`로 만들 수 없다. 원래는 개발자가 `implements`로 구현 클래스를 직접 짜야 한다. Spring Data는 `JpaRepository<Employee, Long>`에서 **엔티티와 id 타입**을 보고, 그 구현 클래스를 **앱이 켜질 때 자동으로 만들어서** 주입해 준다.
